# Minion Humanizer（宠物拟人）

把**你自己召唤的宠物（minion）**改成人类骨骼模型，于是它身上就能套 Glamourer / Penumbra 那套人形换装链路，并且全程跟着你跑。

这就是以前 Glamourer 那个 "Turn Human" 按钮做的事——它被作者在 **1.6.0.0** 版本里删掉了。这个插件是它的独立重写版，只做这一件事，并且专门处理掉了当初被删的三个理由。


**v1.8：修好上下坐骑 + 界面显示版本号 + 快照备份流程**

- **上下坐骑不再变回原形**。之前 `Enumerate` 只对 **NPC 类目标**做了"骑乘中一刀切"，**宠物被漏掉了** —— 骑乘时宠物处于「被安置在玩家身上」状态，游戏不绘制它，此时对它做任何事（**包括 v1.7 的就地刷新**）都是和游戏抢同一个对象。现在改成**整个枚举在骑乘期间停摆**，一个目标都不碰。
- **落骑瞬间强制恢复**。骑乘期间游戏会把模型整理回随从形态，落骑那一刻必须立刻重新施加，否则要等退避计时器（最长 30 秒）。新增 `OnDismounted()`：检测到落骑就把所有目标的退避计数、退避时刻、节流时刻一起清零，并强制巡检。
- **界面底部显示版本号**（`v1.8.0`），取自程序集 AssemblyVersion，与 csproj 的 `<Version>` 一致——不用再猜装的是哪一版。
- **每次发版自动快照**。见下面的「版本与备份」。

## 版本与备份（v1.8.0 起）

**v1.8.0 是当前"已验证全部正常"的版本**——上下坐骑、切设计、重复施加、附加设计显隐、走路贴地、体型缩放全部通过（2026-10-07）。

**当前推荐版本见 `.snapshots/LATEST_GOOD.md`。** 每个发布版本都有一份完整快照：

```
.snapshots/v1.8.0/
├── src/       完整项目源码（结构与项目内 MinionHumanizer/ 一致，可直接编译）
├── dist/      MinionHumanizer.dll + .json（直接丢进 Dalamud dev 目录）
└── README.md / build.cmd / build.ps1 / snapshot.cmd
```

发版用 `snapshot.cmd`，不要手动改版本号：

```bat
snapshot.cmd 1.9.0.0     指定版本号
snapshot.cmd patch       1.8.0 -> 1.8.1
snapshot.cmd minor       1.8.0 -> 1.9.0
snapshot.cmd major       1.8.0 -> 2.0.0
```

它会依次：改 `<Version>` → 编译 → 复制产物到 `dist/` → 写快照。**编译失败则不产生快照。**

**两条铁律：**

1. **回退只从快照取源码**，不要按文档逆向改代码——逆向会连带删掉锚点之间的字段和构造函数。
2. 每发一版，在 `.snapshots/LATEST_GOOD.md` 里写清**验证了什么**。只写"编译通过"不算验证。

**v0.3 修复与新增：**

- **Glamourer 设计拉取失败已修**——原因是设计内容走了 `GetDesignJObject`（要把 Newtonsoft 的 `JObject` 过 Dalamud IPC，序列化器未必吃这个类型）。改走 `GetDesignBase64`（纯字符串，万无一失）；另外下拉框"看起来选中了但配置里是空 Guid"的坑也修了（现在会自动选中第一项并在聊天框提示），失败原因会直接显示在设置窗口里。
- **「一动就浮空」已修**——静止时有效是因为游戏此时不重算绘制对象位置；移动时它每帧重算并覆盖。现在额外写 `GameObject.DrawOffset`（游戏自己摆绘制对象时用的偏移字段），两条通路同时生效。
- **默认待机动作（Idle）可改**——「姿态 / 表情」页新增：生效方式（不改 / 始终 / 仅静止）+ 待机 ID 输入 + **「用我当前的待机」**（一键抓本地玩家此刻的 base 时间轴，种族体型天然匹配）+ 停止待机。

> ⚠️ **先说清楚**：这是第三方插件，处于游戏 ToS 的灰色地带。仅对你自己的宠物生效，纯客户端视觉改动。使用风险自负。

**v0.4 整体优化（修掉几个真 bug）：**

- **换设计不生效**——这是最影响使用的一个：宠物已经是人形时巡检会判定"无需处理"，所以在设置里换 Glamourer 设计后要换图才看得到变化。现在任何外观相关改动（切设计、切身体/装备来源、点「立即应用」）都会显式请求重施。
- **换区清空跟踪 = 永久失去还原能力**——副本内换区时宠物往往还活着，清掉快照后 `/mhuman revert` 会把人形当"原样"写回，再也变不回蝴蝶。现在换区只标记重施，记录留给巡检清理。
- **贴地补偿无法还原**——v0.3 每帧写 `DrawOffset` 但没存原值，还原后仍会偏移。现在补偿前先存原值，关掉补偿/还原/宠物消失时写回。
- **待机可能被游戏清掉**——原来贴一次就不管了；现在每 30 帧重确认一次 `BaseOverride`。
- **抖动保护**——如果签名没命中导致游戏反复把模型改回去，原来每次巡检都会重绘（闪烁 + 失败计数耗尽）；现在超过 3 次就停止重试并在日志里点名原因。
- **每帧零分配**——姿态控制器改用复用的缓冲列表，不再每帧 `ToList()`。
- **状态字典会清理**——宠物消失后 `_savedMotion`/`_lastPosition`/`_idleApplied`/`_savedDrawOffset` 都会回收。
- **自检报告**——`/mhuman diag` 或设置页的「输出自检报告」会列出每只宠物的实时 `ModelCharaId`、`DrawOffset`、绘制对象是否存在、被改回次数、短路是否命中。排查"到底生效没有"不用再猜。

**v0.5：召唤物（宝石兽 / 小仙女） + 坐骑隔离 + 设计读取路径修正**

- **召唤物（宝石兽 / 小仙女）可拟人化**——它跟宠物不一样：对象表里它是 **BattleNpc（NPC 类 actor）**，不是 `Companion`，没有 `Owner` 字段可校验。所以走另一套更严格的识别：**你显式指定名字/ID** + 紧跟你身边（默认 12 yalm）+ 没死 + 没被谁盯着，而且**默认关闭**。设置页有「探测身边的 NPC 候选」按钮，列出名字/类型/ID/距离，照着填即可。
- **坐骑不再被视觉修正影响**——跟宠坐骑（`CompanionType.FollowMount`）现在只做拟人化，**不参与贴地补偿 / 体型缩放 / 表情 / 待机**。坐着时把坐骑压到地下或缩小只会碍事，这是硬性排除，不是开关。
- **设计读取路径修正**——`GetDesignBase64` 返回的**不是 JSON**，而是 Penumbra 的压缩容器（`CompressionFunctions.ToCompressedBase64(json, 6, Uncompressed)`，首字节就是版本号 6）。现在改为**直接读 Glamourer 写盘的设计文件**（`%APPDATA%\XIVLauncherCN\pluginConfigs\Glamourer\designs\{设计ID}.json`，文件名就是设计 ID，内容就是设计 JSON），不依赖 IPC、不依赖 Glamourer 是否在运行，拿到的永远是最新保存的内容。

**v0.6：坐骑视觉修正彻底隔离 / 待机抽搐修复 / 坏道具不再废掉整份设计 / UI 重构**

- **视觉修正只作用于真正的宠物**。之前把召唤物（宝石兽 / 小仙女）也放进了白名单——但它是**能骑的鸟**，压到地下或缩小显然不合适。现在 `AllowVisualPuppetry()` 只对 `Minion` 返回 true：跟宠坐骑、召唤物（宝石兽 / 小仙女）都只做拟人化，贴地/缩放/表情/待机/调速一律不碰。`RestoreDrawOffset` 也加了同样的闸门。
- **待机抽搐已修**。原因是"逐帧比较位移"的朴素判断：宠物待机时有微小位置抖动（AI 重算路径、服务器纠正），待机就反复贴上/撕掉。现在改成**带迟滞的状态机**：位移做指数平滑、连续 12 帧静止才贴待机、连续 6 帧移动才撕掉、切换后 30 帧冷却；并且每帧只写 `BaseOverride`、**不重播时间轴**（重播会让动画从头开始 visibly 卡一下）。
- **坏道具不再废掉整份设计**。日志里那个 `ArgumentOutOfRangeException: rowId 4293966911` 是这么来的：设计 JSON 里的 `ItemId` 是 Penumbra 的 `CustomItemId`（ulong），里面塞了三种"不是道具行号"的值——带 `CustomFlag`(1<<48) 的 mod 物品、`0xFFFFFF7x` 的空槽标记、超出表范围的值。现在这些一律判为无效（该槽位按裸装处理），并且每个槽位单独 try/catch，一个坏槽不再让整份设计失败。
- **消除了 91ms 卡顿**：读盘 + 解析 JSON 是毫秒级操作，之前每次施加都在主线程同步做，连续几只目标就卡出 HITCH。现在按"文件最后写入时间"缓存解析结果。
- **UI 重构**：改成 5 个页签（外观 / 召唤物（宝石兽 / 小仙女） / 姿态·表情 / 安全 / 状态·自检），每页内部用「分组 + 缩进」明确父子关系；总开关和立即施加/还原提到窗口顶部常驻；召唤物（宝石兽 / 小仙女）独立成页并按 ①总开关 → ②指定目标 → ③安全范围 → ④其它 分步。

**v0.7：待机"完全失效"的真 bug 已修 / 陆行鸟可独立配置 / 跟宠坐骑状态可见**

- **待机动作之前完全没生效过**——这是我上一版重构引入的真 bug：只有 `WhenStill` 分支会去置 `state.Active`，于是**`始终`模式下 Active 永远是 false**，应用分支永远进不去。现在三种模式的 Active 推导统一处理，`始终` 模式终于能贴上。
- **召唤物（宝石兽 / 小仙女）可以有自己的外观设计、待机动作、表情**：陆行鸟页新增「④ 外观（可与宠物不同）」「⑤ 待机动作（可与宠物不同）」两组；不勾"使用与宠物不同"时就跟随宠物。表情页加了「播放给」选择器（宠物 / 召唤物（宝石兽 / 小仙女）），命令也支持：`/mhuman emote 挥手 bird`。
- **跟宠坐骑开没开一看便知**：安全页新增「当前正在处理的目标」清单，直接列出每个目标的**名字 / 类别 / 是否已拟人化**。以前只有一个开关，根本看不出它到底有没有被识别到。
- 视觉修正（贴地 / 缩放）仍然只对**真正的宠物**生效；表情与待机扩展到宠物 + 召唤物（宝石兽 / 小仙女）；跟宠坐骑两者都不参与。

**v0.8：坐骑问题根治 / 换区重试修复 / 缩放持久化 / 菜单重构**

- **坐骑被视觉修正影响——真凶找到了**：坐骑在对象表里也是 `BattleNpc`，而且它必然紧贴着你（距离 0~1 yalm）。所以召唤物（宝石兽 / 小仙女）那套"名字/ID 匹配 + 距离内"的规则**会把你正骑着的那只坐骑一起捞进来**。现在加了两道铁律：`ICharacter.CurrentMount` 有效（即骑乘中）时**整个 NPC 分支直接停摆**，并且 `PuppetController.Tick` 骑乘时整体停手、还原所有修正。骑乘时总览页会显示提示。
- **换区后宠物有概率不再拟人化——真凶是"永久放弃"**：抖动保护写成了"被改回超过 3 次就永远不再管这只宠物"。换区时游戏必然重建一次模型，攒够 3 次就彻底放弃。现在改成**指数退避重试**（1/2/4/8…最多 30 秒一次，永不放弃），模型恢复正常即清零；另外换区时会先清理掉对象已失效的死跟踪记录（它们会挡住新宠物）。
- **体型缩放随机失效——因为只写了一处**：游戏每帧会依据 actor 的缩放重算绘制对象的变换，只写 `CharacterBase->Scale` 会被悄悄算回去。现在**同时写 `GameObject->Scale`（权威、持久，绘制对象重建后自动继承）和 `CharacterBase->Scale`（当帧生效）**，并保存原值供还原。`CharacterBase.ModelScale/GlobalScale` 是 protected，写不了也不该写。
- **召唤物（宝石兽 / 小仙女）也有独立的视觉修正**：新增「对召唤物（宝石兽 / 小仙女）也应用视觉修正」开关 + 独立的贴地补偿与体型缩放，与宠物各调各的。
- **菜单重构**：之前所有设置混在三页里、宠物和陆行鸟的选项互相穿插。现在改成**一页只负责一个目标**——总览 / 宠物 / 召唤物（宝石兽 / 小仙女） / 高级。每个分组有一句说明（这就是父子关系），每组下面直接显示"当前生效值"，不用点开就知道状态。

**v0.9：体型缩放语义修正（参数与实际对不上的根因）**

上一版把缩放参数当**绝对值**写进内存，这是"参数显示 1、体型却小得离谱（或大得离谱）"的根因。游戏给每只宠物定的**原始缩放并不相同**（宠物往往远小于 1），把倍率当绝对值写就抹掉了这个原始尺寸。三个不变量现在全部成立：

- **参数是倍率，不是绝对值**——实际缩放 = 游戏原始基准 × 倍率。`1.00` 严格等于"游戏原样"。
- **倍率回到 1.00 会严格还原**——之前只还原了 actor 缩放、**漏了绘制对象缩放**，所以调小过一次之后绘制对象永远保持那个小尺寸，而参数却显示 1（"参数是 1 但小的不行 / 调完还是 1 但大得离谱"就是这个）。
- **绘制对象重建后基准自动重捕获**——拟人化重绘与换区都会换掉绘制对象，旧基准随即作废。现在通过 `Redrawn` 事件 + 换区纪元（`Plugin.VisualEpoch`）丢弃基准，下一帧按新对象重新捕获；捕获时还做区间校验（缩放不可能为 0、负数或几十倍），不合法就下一帧重试，避免把未初始化的脏值当基准。

同源的**贴地补偿**也一起修正：偏移量现在是"基准 + 增量"，不再抹掉 `DrawOffset.Y` 的原始分量，绘制对象位置每帧从 actor 位置重建（不会累积漂移）。

设置页的滑条标签改为「体型缩放倍率 ×N.00」并注明 `1.00 = 游戏原始体型`。自检报告新增**实时读数**：`缩放 参数×N.00 实际actor=X.XXX 绘制=X.XXX`——参数与实际对不上时一眼就能看出。

**v0.10：实时同步 Glamourer 设计 + 修复"反复施加/还原后沉进地里"**

- **实时同步设计**：外观页新增「实时同步（在 Glamourer 里改完自动应用）」。在 Glamourer 里改设计并保存后，宠物外观**自动跟上**，不需要回插件点任何按钮。
  - 实现方式：**监视设计文件的最后写入时间**（`pluginConfigs\Glamourer\designs\{Guid}.json`）。Glamourer 没有暴露"当前正在编辑哪个设计"的接口，只提供"按 GUID 取设计"，所以文件时间戳是唯一可靠的"它变了"信号。
  - **带防抖**：Glamourer 保存时可能分几次写文件，看到时间戳变化就立刻读会读到半截 JSON、解析失败并让外观闪回"照抄我自己"。所以检测到变化后要等时间戳稳定若干轮（默认 0.8 秒）才判定写入完成。
  - **有节流**：每 0.5 秒问一次文件系统，并且只在"开了实时同步 + 正在用设计 + 有已拟人目标"时才工作。
  - 宠物与召唤物（宝石兽 / 小仙女）各看各的设计文件，任一变化都会触发对应目标重新施加。
  - 确认变化后会强制丢弃解析缓存并调用既有的重施通道（带冷却），**不会**每次保存都重绘一次。
- **修复"反复点施加/还原后宠物跑进地里"**：这是上一版引入的**基准泄漏**——`Forget` 和换区处理直接 `Clear` 掉偏移/缩放基准，**却没有先把内存里的修正值写回原值**。下一轮重新捕获时把这个残留值当成"游戏原始基准"，于是每次施加/还原/换区都往下沉一层。
  - 现在顺序统一为**先还原、再清记录**（`RestoreAllOffsets` / `RestoreActorScale`）。
  - 另外"还原操作"本身会触发重绘进而丢弃基准，而巡检随后立刻重新施加——这条时序也用 `BeforeRestore/AfterRestore` 标记跳过了，否则每次点"还原"就多沉一层。
  - 顺带修掉一个隐患：还原路径里硬编码 `TargetKind.Minion`，会让**召唤物（宝石兽 / 小仙女）被类别守卫挡掉、永远还原不回去**；改用 `VisualHandle()` 表示"不按类别过滤"。

**v0.11：修复贴地补偿"按一次施加就多沉一层"（双重补偿）**

上一版补了基准泄漏，但**根因其实还有一层**：贴地补偿当时有**两条通路同时写**——

1. `GameObject.DrawOffset.Y = 基准 + 偏移`
2. `DrawObject->Position = actor位置 + 基准 + 偏移`

而游戏渲染时会**同时采用两者**，于是同一个偏移被算了两遍。更糟的是通路 2 每帧都写、通路 1 也在写，两者的"基准"互相污染，于是**按一次「立即施加」就多沉一层**（用户实测：贴地补偿 -1，连按三次变成 -3）。

诊断数据能看出这一点：`DrawOffset.Y=-3.00` 恰好等于配置值——说明单次写入没错，是**叠加**。

现在**只保留一条通路**（每帧把绘制对象位置重建为「actor 真实位置 + 偏移」），并且：

- **只以 actor 位置为唯一基准**，不读也不累加上一次的绘制对象位置 → 结构上不可能累积；
- **不再碰 `DrawOffset`** → 「补偿值 = 实际下沉量」成为一对一关系；
- 还原时同时把绘制对象位置放回 actor 真实位置（否则会一直停在偏移后的高度）。

代价：移动中游戏若重算绘制对象位置，可能短暂覆盖我们的值（把补偿调大一点即可）。自检报告现在直接给出**实际下沉量**并与配置值并列（`下沉=-1.00(配置 -1.00)`），两者应当完全一致；不一致就说明又有叠加或漂移。

**v0.12：修复"走起来就浮空"（贴地补偿改为自适应通路）**

上一版把补偿收敛成"只写绘制对象位置"，解决了叠加，但引入了新问题：**游戏在移动时会重算绘制对象位置，把我们的值覆盖掉，于是走起来又浮空**（静止时正常）。

这一版不再猜测，而是**运行时实测游戏到底认不认 `DrawOffset`**：

- **通路 A（`DrawOffset` 为权威载体）**——它是游戏自己摆绘制对象时读的字段，所以移动中的重算会天然带上它，走起来不会浮空。每帧用**绝对值覆盖**（基准 + 偏移），不是累加，所以不可能叠加。
- **纠偏（绘制位置拉回目标）**——每帧检查实际高度是否等于「actor 位置 + 偏移」，不等就拉回。若游戏采纳了 `DrawOffset`，这一步是幂等的（同值不写）；若不采纳，它就是唯一生效的通路。
- **自适应探测**——第一帧记录纠偏前的实际高度差；下一帧若该差值已经等于设定的偏移量，说明 `DrawOffset` 被采纳（走 A）；若仍接近 0，说明游戏把位置重算回去了（只靠纠偏）。换区或还原后会重新探测。

**决定性的设计原则：两条通路始终指向同一个目标值**，所以它们是"收敛"关系而非"叠加"关系——这是无论哪种通路都生效、且永不累积的根本保证。

自检报告新增 `补偿通路=` 一行，会直接告诉你结论：

- `DrawOffset 已被游戏采纳` → 走起来也应该稳；
- `游戏不接受 DrawOffset，靠逐帧纠偏` → 移动中可能有一帧的抖动，但会被立刻拉回；
- `探测中` → 前一两帧的中间状态。

**v0.13：彻底放弃改`DrawOffset`（治"走起来反而下沉"）**

上一版改用 `DrawOffset` 当权威载体，结果从"浮空"变成了"下沉"。这次终于看清了根因：

**`DrawOffset` 不是"给插件用的偏移字段"。** 它与 `NameplateOffset` / `CameraOffset` 同级，是**游戏自己摆绘制对象时的通用偏移**——飞行宠的悬浮高度正是靠它表达的。我们覆写它等于**和游戏抢同一个字段**：静止时游戏不重算所以看着对，一移动游戏按自己的逻辑重算（叠加或覆盖）→ 方向相反的下沉。

所以最终形态是**完全不碰 `DrawOffset`**，只写绘制对象位置，并且：

- 每帧从 **actor 的真实位置**重算绝对目标值（`actor.Y + 你的偏移`），不读也不累加上一次的结果；
- 只纠正**高度这一个维度**，X/Z 交还游戏（那部分不该插手）；
- 纠偏容差放宽到 **2 cm**——游戏移动时会按自己的逻辑插值/重算绘制位置，卡太死会与它每帧互相拉扯，反而表现为抖动或"看起来没贴住"。

现在「补偿值 = 实际下沉量」严格一对一，无论施加/还原多少次都不可能漂移。

自检报告会显示 `DrawOffset.Y` 的真实值（应当保持游戏自己的数值，我们不改）以及 `下沉=X(配置 Y)`，两者应当一致。

**v1.0：视觉修正回退到最简形态（actor 层完全不再触碰）+ 关闭时全量还原**

这一版做了两件事。

**① 视觉修正回退。** v0.8~v0.13 我为了追求"稳定持久"去写了 actor 层（`GameObject.Scale`、`GameObject.DrawOffset`），结果连续踩坑：缩放越来越小、走起浮空、走起下沉。回头看，根子是同一个——**actor 层是游戏的地盘**（命中判定、跟随距离、特效挂点、悬浮高度都靠它），插件去改就是在和游戏抢字段，症状还随"游戏什么时候重算它"变化。

v1.0 回到最简形态：**只写绘制对象（`CharacterBase`），actor 层一个字节都不碰。**

- 贴地补偿：每帧把绘制对象的 Y 重算成 `actor 位置 + 你的偏移`，容差 1cm，只改 Y 不动 X/Z；
- 体型缩放：只写绘制对象的 Scale，绝对值写入（`基准 × 倍率`），基准只在绘制对象从未被写过时捕获一次，之后永不重新采样——**这一条正是治"反复开关越来越小"的关键**（之前重新采样会读到我自己写的值，基准被污染成上次的结果，于是每次开关乘一次倍率）。

**② 关闭时全量还原**（你要求的新增）。之前只有模型会还原，位置和缩放停在偏移状态。现在三处都会还原：

- **关掉设置里的「启用」开关** → 所有目标的绘制位置放回 actor 真实位置、缩放放回基准、待机与表情解除；
- **禁用 / 卸载插件** → 同上，而且**顺序修正**为「先还原模型（会重建绘制对象）→ 再还原位置与缩放」，否则还原会被重建覆盖；
- 还原时会遍历对象表而不是内部缓冲，确保卸载时那个缓冲为空也能覆盖到目标。

**保留的功能**（全部不受影响）：召唤物（宝石兽 / 小仙女）拟人化与独立外观/待机/视觉修正、设计实时同步、换图自动重施、骑乘隔离、菜单四页签结构、自检报告、表情/动作控制。

**v1.1：贴地补偿恢复两条通路（治"走路浮空"）**

v1.0 只写绘制对象位置，静止正常但**走起来游戏会重算绘制位置 → 又浮空**。这一版按你说的"用以前的方法"——恢复 v0.3 引入的两条通路：

- **(a) `GameObject.DrawOffset`**（权威）：游戏摆绘制对象时会读它，所以移动中的重算天然带上它，这是"走动时不再浮空"的关键；
- **(b) 绘制对象 Position**（兜底纠偏）：静止时立刻见效。

但恢复时必须避开之前踩过的两个坑：

**① 基准必须在写入之前捕获。** 我最初把捕获放在写入之后，读到的就是自己刚写的值 → 基准被污染成"上次的结果" → 每次开关叠一层（就是之前"设 -1 变 -3"的原因）。现在写入前捕获，且写成**绝对值 `基准 + 偏移`**（不是累加），天然幂等。

**② (b) 的目标值直接取 (a) 算出来的结果**：`targetY = actor.Y + DrawOffset.Y`。这样 (b) 只是"把游戏本来就会摆到的位置补上"，两条通路指向**同一个位置** —— 是收敛关系，绝不会叠加成两倍。

还原路径同样对称：`DrawOffset` 写回原值，绘制位置回到 `actor + 原偏移`。

体型缩放仍保持 v1.0 的做法（只写绘制对象、不碰 actor 缩放、基准只捕获一次）。

**v1.2：修复"切设计后变回原样，要重新开关才恢复"**

**根因是重施请求被"抖动退避"吃掉了。** 巡检里本来有一条保护：游戏把模型改回非人形时，退避重试（1/2/4/8…秒）以免每帧重绘造成闪烁。

但**切设计恰好会触发这条路径**：重绘过程中游戏会短暂把模型退回非人形，于是这一轮巡检命中退避分支被直接 `continue` 掉——用户的重施请求就这么丢了。模型停留在非人形态，只能靠重新开关总开关恢复（那条路径不走巡检判定）。

修法：**显式重施请求优先于退避。** 判断加上 `&& !tracked.NeedsReapply`——只有"游戏自己莫名把模型改回去"才退避重试，用户主动要求的重施（切设计 / 改外观 / 改身体装备来源）立刻执行。

同时加了两道加固：

- **重施冷却不拦显式请求**——用户刚点完就该立刻生效；
- **`Apply` 调用加最外层 try/catch**——绝不因一次异常让 `NeedsReapply` 永久卡住（那同样会让宠物卡在非拟人态）。

**v1.3：修复"原样快照被误删"（这是前两版症状的共同根因）**

v1.2 修的是"重施请求被退避吞掉"，但没解决更底层的问题——**跟踪记录连同原样快照被误删**。一旦快照丢了，"原样"就变成了"当前状态"（已经是人形），于是：

- 重新施加时 → 用被污染的快照 → 宠物闪回原型；
- `/mhuman revert` → 把人形当原样写回 → 宠物再也变不回原形。

**为什么会误删？** 归属校验用的是 `Companion->Owner`。但**拟人化重建绘制对象的那几帧里，`Owner` 暂时读不到本地玩家**（对象正在重建，`Companion` 子结构没填好）。这一瞬间它被判定为"陌生随从"踢出候选列表 → 巡检末尾的清理看到"不在 seen 里" → 连同快照一起删掉。

修法三道：

1. **容忍重建期的 Owner 不可读**——`Owner` 不匹配时，若"该地址已被我们跟踪且 EntityId 一致"就不踢（陌生人仍然拦掉，安全性不降）。
2. **清理加 5 秒宽限期**——只有"连续这么久没被枚举到"才真正丢弃，瞬态消失不再误删。
3. **快照污染检测**——`Apply` 前检查快照的 `ModelCharaId`：若为 0（说明记的是人形），直接拒绝使用并重新捕获，绝不拿它当原样写回。

另外新增一条恢复命令：**`/mhuman resnapshot`**——强制丢弃旧记录、以当前状态重建原样基线。

如果你手上的宠物**已经处于快照污染状态**，按这个顺序恢复一次：

```
/mhuman off        ← 关掉功能，让它变回原形（此时它就是蓝闪蝶了）
/mhuman resnapshot ← 以原形为基准重建快照
/mhuman on         ← 再开启，重新拟人化
```

从此以后不会再复发。

**v1.4：按陆行鸟的思路重做宠物识别（"召唤物（宝石兽 / 小仙女）一切正常"是关键线索）**

**"召唤物（宝石兽 / 小仙女）正常、宠物不正常"这个对比直接指出了根因。** 两者走的是完全不同的识别路径：

| | 召唤物（宝石兽 / 小仙女） | 宠物 |
|---|---|---|
| 对象类型 | `BattleNpc` | `Companion` |
| 识别方式 | 名字/ID 匹配 + 距离 | 读`Companion->Owner` + `CompanionType` |
| 拟人化后是否失效 | **不受影响**（不读那些字段） | **失效** |

所以问题不是"拟人化把宠物弄坏了"，而是**我们每帧都在重读那些描述"原始随从状态"的字段**——我们把 actor 改成人类模型之后，它们就不再可靠。于是宠物被踢出候选列表 → 原样快照被连带删除 → 一切连锁崩塌。

修法与陆行鸟同思路：**已跟踪的目标直接信任，不再每帧重新判定。** `CompanionFinder` 增加一个钩子，由 `HumanizerService` 注入，返回"跟踪时确定的类别"；`Enumerate` 优先用它，命中就**完全跳过 `Owner` / `CompanionType` 的读取**。只有**未跟踪**的目标才走完整归属校验（安全性不降——陌生随从仍然进不来）。

同时修正 v1.3 引入的一个**严重副作用**：那时的"快照污染检测"在 `Apply` 里直接 `return`，导致**每一次重施都原地不动**——这正是"切设计和重复施加全都变回去"的直接原因。现在改成只记警告、照常施加（施加只需要 customize/equipment，不依赖快照）；只在 `Restore` 路径上拒绝使用污染快照（否则会把人形当原样写回，宠物永久卡在人形）。

至此"设置项全部无效"的三条症状都归到同一个根因：**原样快照 / 跟踪记录在拟人化后被误删**。

**v1.5：重施不再走完整重建（这是"变回去"的真正成因）**

前几版都在"识别跟踪"上打补丁，方向错了。真正的机制是：

```
重施 → 完整重建（DisableDraw → EnableDraw）→ 在已人形的宠物上超时失败
    → Finish 判定失败 → 自动回滚成原形
    → 累计 3 次 → 自动关闭整个功能
```

最后一步就是"**必须重新开关才会拟人**"的来源——功能被悄悄关掉了，用户只看到宠物不对。

**修法参照 Brio**：只有模型或骨架真的变了才重建，否则**就地刷新外观**：

| 情况 | 路径 |
|---|---|
| 第一次变人形 / 换种族性别部族 | 完整重建（写 `ModelCharaId=0` + DisableDraw/EnableDraw） |
| 已是人形，只是换设计、换装备 | `Human.UpdateDrawData()` 就地刷新，**不撤下绘制对象** |

判定依据是"骨架指纹"（`Persona.StructureKey`：种族/性别/体型/部族四个字节）。

另外修掉三处放大问题的行为：

- **不再自动关闭功能** —— 改为越退越久地重试，并把失败原因直接打到聊天框；
- **超时/对象消失不再计入失败**（那是环境问题，不是数据问题，不该触发任何惩罚）；
- **重建完成判定收紧** —— 原来是"DrawObject 非空就算成功"，现在要求绘制对象**可见且确实是人类模型**，撤下后还先等 2 帧（否则会读到还没清空的旧对象，产生"日志成功但画面还是原形"的假成功）。

新增自动修正与诊断：巡检若发现"内存已是人形、但绘制对象不是人类模型"，会自动重新施加；`/mhuman diag` 现在会显示 `画面=Human` 一项，它和 `ModelCharaId` 不一致就说明画面没跟上。

**v1.6 / v1.7：补齐校验阶段，并把「刷新」与「重建」彻底分成两条路**

- **v1.6（切设计）**：v1.4 只改了枚举阶段（`CompanionFinder.Enumerate`），漏了校验阶段（`SafetyGuard.CheckTarget`）。后者每次重施都重读 `Owner` / `CompanionType` / `BehaviorState` —— 拟人化后这些字段不可靠，于是**你点的重施被插件自己的安全校验拦下**。陆行鸟走 `CheckChocoboTarget`，不读这些字段，所以一直正常。现在已跟踪且 EntityId 二次确认过的目标跳过这些校验。
- **v1.6（附加设计不对版）**：直接写 `IsHatHidden` 之类位域属性只改内存标志，**画面不会更新**。改用通知式方法 `HideHeadgear(0, hide)` / `SetVisor` / `HideVieraEars`（Brio 同样用法），且它们不在 `UpdateDrawData` 缓冲区里，顺序放前面。
- **v1.7（上下坐骑后变回原形）**：骑乘时宠物处于「被安置在玩家身上」的状态，游戏不绘制它。此时跑 `DisableDraw → 等 IsReadyToDraw → EnableDraw` 是**永远等不到**的，必然超时回滚 → 停在原形。

  修法是**按是否需要重建分流**：

  | 现状 | 走哪条路 | 需要的条件 |
  |---|---|---|
  | 内存人形 + 画面人形 | 就地刷新外观 | 无（安置/换区边缘都安全） |
  | 模型被游戏重置了 | 完整重建 | 必须避开安置状态，等下坐骑后自动恢复 |

  同时把退避上限从 30 秒压到 5 秒——退避太久就等于"宠物长时间停在原形"。

## 一、它到底做了什么

核心就三行内存写入。宠物是 `ObjectKind.Companion` 类型的 actor，它的外观完全由客户端这两个结构决定：

```csharp
// 1) 模型：0 = 人类基础模型（具体种族 / 性别 / 部族由 CustomizeData 决定）
character->ModelContainer.ModelCharaId      = 0;
character->ModelContainer.ModelCharaId_2    = -1;
character->ModelContainer.ModelSkeletonId   = 0;
character->ModelContainer.ModelSkeletonId_2 = 0;

// 2) 长什么样：26 字节 CustomizeData（在 DrawDataContainer 的 +0x220）
character->DrawData.CustomizeData.Data[...] = customize;

// 3) 穿什么：10 个槽位 × 8 字节 EquipmentModelId（在 +0x1D0）
character->DrawData.EquipmentModelIds[slot] = ...;

// 4) 让游戏按新数据重建绘制对象
go->DisableDraw();
go->EnableDraw();    // 内部会用 ModelContainer + DrawData 现造一个 CharacterBase
```

**换装是白送的**：模型一旦变成人类（`Human` 类型的绘制对象），`DrawData.EquipmentModelIds` 这条链路就对它生效了，装备、染色都正常。

**"全程跟随"也是白送的**：我们从来不碰宠物的位置、AI、行为。它本来就是服务端+客户端 AI 驱动着跟你的，我们只是给它换了一层皮。跟随逻辑一行都没改。（`设置 → 让宠物保持「跟随」行为` 是个额外选项，把 `CompanionMove` 写成 `Obedient`，默认关闭。）

## 二、三个风险是怎么解决的

### 风险 A：会严重干扰同步工具（Mare Synchronos 这类）

**它为什么会发生。** Mare 一类工具的机制是：订阅 Glamourer 的状态、监听 Penumbra 的 collection 分配，然后按 actor 决定"我把谁的什么外观同步给谁"。老实现把非玩家 actor 改成人形之后，同步工具的判定会把它当成一个"玩家"，于是给它套 collection、或者反过来把它的外观当成玩家的外观去上传。更糟的是老实现是**走 Glamourer 的 state 系统**做这件事的——那等于主动把这次改动摆到了同步工具的订阅清单里。

**这个插件的做法。**

1. **完全不进 Glamourer / Penumbra 的状态系统。** 不调用任何 IPC，不写 design，不注册自己的 IPC。同步工具没有任何渠道能看见这次改动，也就没有东西可同步、可上传。
2. **只对 `ObjectKind.Companion` 动手，且必须是 `Companion.Owner == 本地玩家`。** 别的玩家的角色、NPC、玩家自己，一律在结构上被排除。同步工具只会同步"玩家角色"的外观，我们连玩家角色的内存都不碰。
3. **不抢占、不对抗。** 我们不 hook Penumbra 的重绘、不拦截任何同步事件。工具重绘角色时我们只是在下一次巡检里把值重新写一遍——是"重新表达"，不是"打架"。
4. 可选地短路游戏自己的类型限制检查（见风险 B），让外观**稳定**下来而不是反复横跳——同步工具看到的是一致的状态，这本身就是对同步友好。

### 风险 B：可能让客户端崩溃

**崩溃的三个真实来源，逐个封掉。**

| 来源 | 封法 |
|---|---|
| **悬垂指针**：自己造一个 `CharacterBase` 换上去、再负责销毁，一旦时机不对就是野指针 | **完全不自己创建、持有、销毁任何原生对象。** 绘制对象始终由游戏拥有与回收（`DisableDraw`/`EnableDraw` 由游戏实现）。这是结构性的不可崩，不是"小心一点"。 |
| **重入**：在游戏自己正在创建/销毁 actor 的那几帧里去动它的绘制对象 | 重建**分帧**进行：`DisableDraw` → 等 `IsReadyToDraw()` 为真 → `EnableDraw` → 等 `DrawObject` 出现。每步隔一个 tick，带 3 秒超时。另外在角色创建流程、过场动画、换区过程中一律不动手。 |
| **半初始化的"人"**：只改了模型 id 却没给全 `CustomizeData` / 装备，游戏拿着一个残缺的人类去渲染 | 施加时**三个都写**：模型容器 + 26 字节身体 + 80 字节装备（10 槽）+ 四个视觉开关归一。任何一步不成立就整个放弃。而且**默认外观来源是"照抄我自己"**——游戏此刻正在渲染那份数据，所以它必然是合法的。 |

**外加**：任何异常都被吞在自己这一层并立即**回滚**（写回快照 + 重建），连续失败 3 次自动关掉功能。插件卸载时必定还原。宠物消失时丢弃记录。

**还有一个关键点**：游戏内部有一个 `EnforceKindRestrictions`（按类型强制限制外观）检查。非玩家 actor 用人类模型在它眼里是"违规"的，它会试图把模型修回去——修回去的过程就会造成外观抖动，也是最容易连锁出事的地方。这个插件把它在本插件开启期间短路掉（返回 0）。**这个做法不是我们发明的**：Brio 的 "NPC Appearance Hack" 用的就是同一处签名、同一套做法，并且明确写着这样才"不破坏 Penumbra 这类工具"。

> 诚实提示：这是一处**全局**检查。开启期间它对所有 actor 放行，不是只管我们这一只宠物。所以设置里给了三档：`开启期间一直短路`（默认）、`只在 GPose 中短路`、`不短路`。功能关闭或插件卸载立刻恢复原函数。嫌它影响面大的话，改成"只在 GPose 中短路"，或者干脆关掉——功能仍然可用，只是可能会看到宠物外观闪烁。

### 风险 C：可能往服务器发错数据

**先说清机制。** 客户端真正会**上行发送**的外观数据，只有玩家自己角色的东西：gearset / customize / `FlagSlotForUpdate` 那条链路，以及美容师、角色创建那类流程。**宠物的 `ModelContainer` / `DrawData` 是纯本地派生数据，永远不会进上行包。** 老实现之所以被说"可能往服务器发错数据"，是因为它是从 Glamourer 的 state 系统出发做这件事的，而那个系统同时也在管玩家自己的角色——一旦状态串了，就可能把不属于玩家的东西写进玩家的字段里。

**这个插件的封法（是结构性的，不是靠自觉）：**

- **`ObjectIndex == 0` 直接拒绝**，`ObjectKind != Companion` 直接拒绝，`Owner != 本地玩家` 直接拒绝。也就是说它**在类型层面就无法触碰玩家角色**。
- **在 `ConditionFlag.CreatingCharacter`（角色创建/美容流程）时一律不动手** —— 那正是客户端真的在本地与服务器之间交换外观数据的时刻。
- 不订阅、不写任何 gearset / inventory / playerstate 相关的数据。
- 不注册 IPC，所以别的插件也无法通过我们来间接改玩家。

## 三、重新构建（改了代码之后）

### 一条命令

```
ffxiv-minion-humanizer\build.cmd
```

> **注意**：不要直接运行 `build.ps1`。这台机器的 PowerShell 执行策略是默认的 `Restricted`（所有 scope 都是 `Undefined`），直接 `& .\build.ps1` 会被拒绝执行并返回 exit 1，什么都不做。`build.cmd` 会用 `-ExecutionPolicy Bypass` 启动它。

`build.cmd` 会自动找齐两样东西，正常情况下不需要配任何环境变量：

1. **.NET 10 SDK** —— 优先用系统装的；没有就用本仓库自带的便携版 `../.toolchain/dotnet/dotnet.exe`。
2. **Dalamud 程序集目录** —— 依次尝试：
   - `%APPDATA%\XIVLauncherCN\addon\Hooks\dev\`（国服）
   - `%APPDATA%\XIVLauncher\addon\Hooks\dev\`（国际服）
   - 环境变量 `DALAMUD_HOME`

产物会被收集到 `dist/MinionHumanizer/`。

```
build.cmd Debug         # Debug 构建
build.cmd Release -Zip  # 额外打包 dist/MinionHumanizer.zip（自建仓库用）
```

### 便携工具链说明

构建用的 .NET SDK 是解压到 **`../.toolchain/dotnet/`** 的便携版（约 780MB），**没有装进系统、没有改 PATH、不需要管理员权限**。不想要了就整个删掉 `../.toolchain` 目录即可；删掉之后只要你系统里有 .NET 10 SDK，`build.cmd` 照常工作。

### 工程里有个坑，已经填好了

`Dalamud.NET.Sdk` 在 `Sdk.props` 里设置的 `AssemblySearchPaths` 是**立即展开成字面量**的，所以只覆盖 `DalamudLibPath` 并不会改变引用搜索路径——引用会跑去国际服目录找 DLL，然后报一堆 `MSB3245 未能解析此引用`，接着变成 200+ 个 `CS0246 找不到类型`。`MinionHumanizer.csproj` 里已经把国服路径自动识别 + `AssemblySearchPaths` 补全都写进去了，所以开箱即可构建。

### 方式 2：自建 Dalamud 仓库

1. 用 `build.cmd Release -Zip` 打出 `dist/MinionHumanizer.zip`，传到任意静态托管（GitHub Release 就行）。
2. 编辑根目录的 `repo.json`，把 `DownloadLinkInstall` / `DownloadLinkUpdate` 换成你的 zip 地址，`RepoUrl` 换成你的仓库地址。
3. 在 `/xlsettings → 实验性 → 自定义插件仓库` 里加上你的 `repo.json` 的 raw 地址。

### API Level

当前对应 **Dalamud API Level 15 / .NET 10**（`Dalamud.NET.Sdk/15.0.0`）—— 已确认与你的国服 Dalamud 一致。
如果你以后装了别的版本，改 `MinionHumanizer.csproj` 里的 SDK 版本号即可（例如 API 14 就用 `Dalamud.NET.Sdk/14.0.0`）。

## 四、使用

```
/minionhuman                    切换开 / 关（简写 /mhuman）
/minionhuman on | off           明确开关
/minionhuman status             看当前状态、Glamourer 设计、当前动作、短路是否生效
/minionhuman diag               自检报告（每只宠物的 ModelCharaId / DrawOffset / 抖动次数）
/minionhuman apply              强制重新施加一次（换了设计后用）
/minionhuman revert             立刻把宠物还原
/minionhuman emote <名|ID>      在宠物身上播放表情/动作（如 /mhuman emote 挥手）
/minionhuman stop               停止表情、恢复正常
/minionhuman config             打开设置窗口
```

设置窗口分三页：

- **外观**
  - **Glamourer 设计**：下拉选你在 Glamourer 里保存的设计，勾选即用。装备、染色、帽子/面罩/武器可见性都会带上；主/副手武器默认关（实验性，勾选后生效）。Glamourer 没开时自动回退到下面的来源并在聊天框提示。
  - **回退外观来源**：`照抄我自己`（推荐）/ `自定义快照` / `内置默认值`；装备 `照抄我自己` / `裸装` / `自定义快照`。
- **姿态 / 表情**
  - **贴地补偿**：飞行类宠物（蓝闪蝶等）变人后浮空时往负数拉，直到站在地上。0 = 不修正。
  - **体型缩放**：0.2 ~ 2.5，只作用于渲染层。
  - **表情列表**：来自游戏数据（国服中文名），可搜索，点击即播；配「停止动作」「暂停」「1x 速度」。换装/重绘会打断动作，插件会自动重播一次当前动作。
- **安全**：短路范围、坐骑/跟宠、强制跟随、自动重施、巡检间隔、失败上限、聊天/日志输出。

**设计解析的格式依据**（对着 Glamourer 1.7.1.4 源码与 Penumbra.GameData 核实）：
`Glamourer.GetDesignJObject` 返回的 JSON 中，`Customize` 段的键是 `CustomizeIndex` 名（Race/Gender/…/FacePaintColor，共 37 项），每个值形如 `{"Value": n}`；`Equipment` 段的键是槽位名（Head/Body/…/LFinger + MainHand/OffHand + Hat/Visor/Weapon/VieraEars 元开关），每项含 `ItemId`/`Stain`/`Stain2`。道具 ID → 模型的换算用 Item 表的 `ModelMain`（防具：低 16 位 set、16-23 位 variant；武器：低 16 位模型、16-31 位类型、32-39 位 variant，即 Penumbra `EquipItem.FromArmor/FromMainhand` 的同一套打包）。

## 五、已知限制 / 我不保证的事

老实列出来，别到时候踩坑：

1. **代码已经编译通过，但还没有在游戏里跑过。** 编译是**对着你机器上真实的国服 Dalamud 程序集**做的（`.NET SDK 10.0.401`、`%APPDATA%\XIVLauncherCN\addon\Hooks\dev\`），结果是 **0 错误 / 0 警告**。编译过程中实际修掉了这些（都是真错，不是猜的）：
   - `IClientState.IsBetweenAreas` **不存在**（已用真实 `Dalamud.dll` 核实 `IClientState` 的成员只有 `IsGPosing` / `IsLoggedIn` / `IsPvP` / `MapId` / `TerritoryType` 等）→ 换区判断统一走 `ConditionFlag.BetweenAreas` / `BetweenAreas51`。
   - **迭代器方法里不能直接解指针**（`CS0214`，即使类和方法都标了 `unsafe`）——`yield` 的方法体会被改写成状态机类型，而它不继承外层的 unsafe 上下文 → 把指针判断抽成独立的 `unsafe` 方法 `IsOwnedMinion()`。
   - `Dalamud.NET.Sdk` 的 `AssemblySearchPaths` 不跟随 `DalamudLibPath` 覆盖（见上一节的"坑"）。
   - 顺带用元数据核实了结构体真实布局：`EquipmentModelId` 是 **8 字节**（`Id` +0x00 / `Variant` +0x02 / `Stain0` +0x03 / `Stain1` +0x04），`CustomizeData` 是 **26 字节**，`DrawDataContainer` 总大小 `0x268`。
   
   **另外自查时抓到一个真实的逻辑 bug，已修**：原来卸载路径走的是分帧重建（`BeginRebuild` 里先 `DisableDraw`，再靠 `RunOnTick` 等下一帧 `EnableDraw`），并且在注释里假设"即使插件被卸载，这次重建也能自己跑完"。**这个假设是错的。** `IFramework` 是插件作用域的（`Dalamud.Game.FrameworkPluginScoped`，实现 `IInternalDisposableService.DisposeService`），插件卸载时 Dalamud 会一并处置掉尚未执行的 `RunOnTick` 回调 —— 结果是：卸载瞬间只完成了 `DisableDraw`，`EnableDraw` 永远不会到，**宠物会永久隐形**。现在卸载路径改为同步收尾（写回快照 + 背靠背 `DisableDraw`/`EnableDraw`，出错还会补一次 `EnableDraw`），不再依赖任何后续帧。
   
   **但"能编译"不等于"效果对"。** 模型是否真的变得像人、动作是否别扭、装备染色是否正常，这些必须进游戏看。第一次试请按第零节的建议在安全区小步走。
2. **`EnforceKindRestrictions` 的签名是抄 Brio 的**，没在新版本游戏上验证过。签名不命中时插件会优雅降级（日志里警告一句，功能照常），只是可能看到外观抖动。`/mhuman status` 会直接告诉你签名有没有命中。
3. **宠物被安置在玩家肩上/头上时不动手**（`BehaviorState.Place`），会等到它下来。
4. **人形宠物不会有人的行为**：它还是宠物的 AI。走路动画、待机动作都是宠物那套（用的是人形骨骼绑定的动作，看起来可能有点怪）。想让它做人的表情/动作，用「姿态 / 表情」页的表情列表或 `/mhuman emote`——播放期间它进入动画锁定，AI 不会打断；`/mhuman stop` 恢复。贴地补偿与体型缩放是**每帧覆写渲染层**实现的，随时归零即恢复。
5. **Glamourer 设计是"快照式"的**：拉取那一刻的设计内容。你后来在 Glamourer 里改了设计，需要重新施加（关开一次，或换图）才会用新内容。同样，Glamourer 里删掉该设计后，本插件会回退到「照抄我自己」。
6. **不要对别人的宠物动手。** 功能上做不到（`Owner` 校验），道义上也不该。
6. 插件卸载时会自动还原，但如果游戏崩了没来得及还原——不用担心，宠物外观本来就是每次重新召唤时从零构建的。
7. `MinionHumanizer.json` 里的 `Author` 和 `RepoUrl` 还是占位符（`your-name`）。自己用不影响，要发布的话改掉。

## 安装成「正式插件」（启动自动加载、可在 /xlplugins 里更新）

插件原本放在 Dalamud 的 devPlugins 目录里（`%APPDATA%\XIVLauncherCN\addon\Hooks\dev\`），
它其实每次启动都会被加载，但不会出现在 `/xlplugins` 里，也拿不到更新。
下面的流程把它变成一个标准仓库插件。

### 一次性流程

| 步骤 | 做什么 |
|---|---|
| 1 | 跑 `package.cmd` —— 编译 + 生成 `repo-web\repo.json` 和 `repo-web\MinionHumanizer-<版本>.zip` |
| 2 | 跑 `serve-repo.cmd` —— 起本地仓库服务（`http://127.0.0.1:8787/repo.json`），**保持窗口开着** |
| 3 | 跑 `add-repo.cmd` —— 把仓库地址写进 Dalamud 的自定义仓库列表（自动备份配置） |
| 4 | 重启游戏 → `/xlplugins` → 「可用插件」→ 安装 **Minion Humanizer** |
| 5 | 跑 `remove-dev.cmd` —— 把 devPlugins 目录里的旧副本移走 |

> 第 5 步必须做：dev 目录里的副本还在的话，同一个 `InternalName` 会被加载两次。

装完之后插件落在 `%APPDATA%\XIVLauncherCN\installedPlugins\MinionHumanizer\<版本>\`，
每次启动游戏自动加载，dev 目录和那个本地服务都不再需要。

### 发到 GitHub（可选，之后就能自动更新）

1. 把 `repo-web\` 里的 `repo.json` 和 zip 传到仓库的 `raw` 可访问的路径；
2. `package.cmd --base-url https://你的仓库/raw/路径` 重新打包；
3. `add-repo.cmd --url https://你的仓库/raw/路径/repo.json` 换掉本地地址。

### 改作者名 / 仓库地址

只改 **`repo.json`** 一处即可 —— `tools/make_repo.py` 会把同样的值盖进 zip 内的清单。
